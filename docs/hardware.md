# Hardware reference

Condensed from the upstream
[NXP-Linefollower](https://gitfront.io/r/cristiannxp/xHvo63TFm7h4/NXP-Linefollower/)
project. Go there for the full bill of materials, the shield schematic and

## The robot

| Part | What it is |
|---|---|
| FRDM-MCXN947 | NXP Freedom board, MCX N947 (Arm Cortex-M33, 150 MHz, 2 MB flash, 512 KB RAM) |
| NXPCUP shield | Carries the motor drivers, the sensor comparators and the power supply |
| 2× DC geared motors | 25GA-370, rear wheel drive |
| 2× DRV8833 | Dual H-bridge motor drivers (U2, U3 on the shield) |
| 8× IR line sensors | Reflective, digitised by LM339 comparators (U4–U7) |
| LiPo battery | 7.4 V 2S, 2200 mAh, XT60 connector |
| MP1584EN | Step-down converter, 5 V @ 3 A from the battery |
| Ball caster | Third contact point at the front |

## Motor wiring

Each motor uses one half of a DRV8833 — two control pins, `IN1` and `IN2`:

```
Motor 1   IN1 <- P0_25 / CT0_MAT1  (PWM)      IN2 <- GPIO0.24  (direction)
Motor 2   IN1 <- P0_26 / CT0_MAT2  (PWM)      IN2 <- GPIO0.27  (direction)
```

PWM comes from CTIMER0:

```
CTIMER0
  Match 0 -> PWM period      (~1 kHz: 2343750 Hz tick / 2342 ticks)
  Match 1 -> motor 1 duty
  Match 2 -> motor 2 duty
```

The upstream documentation states the physical mapping as **motor 1 = right
wheel, motor 2 = left wheel**. That is what `source/robot.c` encodes. Verify
it once on your own robot with the wheels lifted (see the comment block at
the top of `robot.c`) — a mirrored sensor bar or swapped motor terminals will
change it, and it must be fixed there rather than in student code.

### DRV8833 truth table

For one motor, with `IN1` driven by PWM and `IN2` held at a fixed level:

| IN1 | IN2 | Result |
|---|---|---|
| 0 | 0 | coast — outputs high-impedance |
| PWM | 0 | forward, strength = duty (fast decay) |
| PWM | 1 | reverse, strength = 100 − duty (slow decay) |
| 1 | 1 | brake — both outputs shorted |

This is why `HbridgeSpeed()` computes the reverse duty as `100 - |speed|`:
with `IN2` HIGH the bridge inverts the PWM itself. It is also why
`HbridgeBrake()` sets direction HIGH *and* duty 100 — that is the brake row,
not full reverse. See the comment block in
[`source/hbridge.c`](../source/hbridge.c).

## Sensors (Workshop 3, not needed yet)

Eight digital signals `S10`…`S17`, read with `GPIO_PinRead()` through the
`BOARD_INITPINS_Sx_GPIO` / `BOARD_INITPINS_Sx_GPIO_PIN` macros generated by
the pin configuration.

The upstream code packs them into one byte as:

```
bit 7   6   5   4   3   2   1   0
    S17 S16 S15 S14 S13 S12 S11 S10
```

with the array laid out left-to-right as `S10 … S17` across the front of the
robot.

Two things must be verified on the real robot before Workshop 3:

1. **Physical order** — confirm `S10` really is the leftmost sensor.
2. **Polarity** — the LM339 comparators may output HIGH or LOW over the line.
   The primer API should normalise this so student code always sees
   `1 = sensor sees the line`, whatever the comparator does.

## Power and safety

- The USB cable powers the **board only**. The motors need the battery.
- Check XT60 polarity before connecting. Never short the battery terminals.
- Charge LiPo cells with a LiPo charger, never unattended, and store them in
  a fireproof bag.
- Lift the drive wheels off the table whenever you flash new motor code.
